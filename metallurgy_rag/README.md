# Smart PDF Extractor

Разбирает технические PDF на размеченные блоки: текст, таблицы, формулы с делением
на физику, химию и математику. Рассчитан на металлургическую и инженерную
документацию, работает с русскими и английскими документами. Готовится как
источник данных для RAG.

## Как устроен конвейер

Документ проходит пять этапов. Каждый следующий опирается на результат предыдущего,
поэтому порядок важен.

**1. Базовое извлечение.** `unstructured` со стратегией `hi_res` размечает макет
страницы: находит рамки блоков и присваивает им классы. Язык распознавания
определяется заранее по текстовому слою — считаются слова длиной от четырёх букв,
иначе химический учебник с его `Fe`, `CO` и `TiCl` выглядел бы наполовину
английским. Если слоя нет или письмо перемешано, передаются оба языка.

**1.5. Пересборка текста из текстового слоя.** Макет, классы и рамки остаются от
`unstructured`, но содержимое блоков берётся напрямую из символов PDF. Это главный
этап для качества формул: распознавание изображения ломает индексы, степени и
греческие буквы, а в текстовом слое они лежат готовыми. Здесь же собираются дроби
по горизонтальным линиям, расшифровываются гарнитуры Symbol и Wingdings,
восстанавливаются высокие скобки и снимаются гомоглифы — русские `Н` и `О` внутри
химических формул приводятся к латинице. Для сканов ветка остаётся прежней: там
результат распознавания единственный доступный источник, и такие блоки помечаются
как ненадёжные.

**2. Графовая кластеризация.** Страница представляется графом, узлы — блоки, рёбра
строятся по пространственной близости: вертикальный зазор, разница левого отступа,
геометрический признак конца абзаца. Связные компоненты ищутся обходом в глубину и
сливаются в один элемент. Пороги задаются в долях настоящего кегля шрифта, а не
высоты рамки. Слияние запрещено, если между кандидатами лежит третий блок.

**3. Классификация формул.** Сначала работает детерминированный разборщик
химической записи: если выражение целиком раскладывается на вещества вокруг знака
реакции, это химия, и модель не спрашивают. Грамматика символов элементов надёжнее
вероятностной оценки — `2NH₄VO₃ = V₂O₅ + 2NH₃ + Н₂О` разбирается без остатка, а
физическая формула из тех же букв нет. Остальное отправляется в модель:
`multilingual-e5-base` даёт представление формулы вместе с окружающим текстом, к
нему добавляются структурные признаки и начертание из текстового слоя, решение
принимает градиентный бустинг. Блоки, у которых текст ненадёжен или от формулы
остался один номер, остаются формулой без подтипа — выдуманный раздел хуже, чем его
отсутствие.

**4. ИИ-инспекция.** Текст блоков страницы отправляется языковой модели через
OpenRouter с просьбой найти ошибки классификации. Найденные исправления применяются
и складываются для дообучения. Картинки страниц модели пока не передаются, поэтому
формулы, вставленные изображением, этот этап не спасает.

## Раскладка проекта

Код собран в пакет `pdfscan`, и подпакеты соответствуют этапам конвейера. Этапы
общаются файлами, а не вызовами: прогон на двухсот документах идёт часами, и
прерванную работу надо продолжать, а не начинать заново.

```

│   ├── extractor.py      конвейер разбора целиком
│   ├── text_layer.py     символы PDF, индексы, дроби, гарнитуры, язык
│   └── export.py         выгрузка блоков в JSONL с координатами
├── formulas/         формулы

│   ├── classifier.py     обёртка модели: представление текста, бустинг
│   ├── train.py          обучение, русский набор примеров
```

## Установка

```bash
python3 -m venv venv
venv/bin/pip install -r requirements/base.txt
venv/bin/pip install -e . --no-deps
```

Для распознавания сканов нужен `tesseract` с языками `rus` и `eng`. Повторное
распознавание формул ставится в отдельное окружение — см. раздел ниже.

## Запуск

```bash
# этап 1: разбор PDF
python -m pdfscan.parse.extractor pdf/ --skip-existing --no-images --no-inspect

# этап 2: повторное распознавание формул — отдельным окружением, см. ниже

# этап 3: очистка корпуса и отчёт
python -m pdfscan.prepare.cli all

# этап 4: индекс и поиск
python -m pdfscan.rag.build build
python -m pdfscan.rag.build search "запрос" -k 5

# переобучение классификатора формул
python -m pdfscan.formulas.train
```

Порядок этапов важен: индекс собирается из результата очистки, а не из исходной
выгрузки, а очистка — из `blocks.jsonl`, которые к этому моменту уже должны
содержать переписанные формулы. Пропустить очистку можно, передав `build` пути к
`blocks.jsonl` напрямую, но тогда в индекс попадут колонтитулы с каждой страницы
и нечитаемое распознавание перевёрнутых таблиц.

Куда смотреть за данными, пакет узнаёт из переменных `PDFSCAN_ROOT`,
`PDFSCAN_PDF_DIR`, `PDFSCAN_OUT_DIR` и остальных из `paths.py`. По умолчанию всё
лежит в корне проекта, а переменные нужны там, где это не так — в Colab и в CI.

Ключи разбора: `--out` — куда складывать результат, `--skip-existing` — пропускать
уже разобранное, чтобы продолжить прерванный прогон, `--no-images` — не рисовать
страницы (быстрее и без гигабайтов PNG), `--no-inspect` — без этапа 4.

Этап 4 стучится в сеть на каждой странице, поэтому на библиотеке из сотен
документов его лучше выключать: разбор всех PDF без него, а инспекция потом
точечно на тех документах, где разметка вызывает сомнения.

Результаты каждого документа лежат в своей папке, повторяющей исходное дерево:

```
out/Литература по медным шлакам/Название книги/
├── blocks.jsonl     сырьё для индекса
├── blocks.xlsx      та же разметка глазами
└── pages/page1.png  страницы с рамками блоков
```

Ключ `OPENROUTER_API_KEY` для этапа 4 читается из `.env`. Для распознавания сканов
нужен `tesseract` с языками `rus` и `eng`.

## Подготовка к RAG

Разбор документа кончается файлом `blocks.jsonl`: одна строка — один блок в
порядке чтения, с классом, страницей, координатами в пунктах PDF, ссылками на
соседей по странице и отметкой, откуда взят текст. Отметка важна: блоки, собранные
из текстового слоя, помечены надёжными, а всё, что пришло от распознавания
изображения, — нет, и такие куски можно отсеивать при поиске.

**Очистка и нормализация.** Снимаются переносы — слово, разорванное на границе
строки, склеивается обратно (в `test.pdf` таких 53); выбрасываются битые символы
`(cid:NN)`, невидимые знаки и разнобой пробелов. У каждого блока получается две
версии текста: исходная для показа человеку и плоская для поиска, где `H_{2}O`
превращается в `H2O`, а `\frac{a}{b}` — в `(a)/(b)`. В химических записях
кириллические двойники переводятся в латиницу, иначе набранная русскими буквами
«Н₂О» не находится по запросу «H2O».

**Единицы измерения** разбираются в метаданные: величина, исходная запись и общее
написание. `117 г/моль` становится `kg/mol`, `286 кДж` — `J` со значением 286000 в
системе СИ. По ним можно отбирать блоки, и запрос на английском находит русский
документ.

**Таблицы** раскладываются построчно: строка «Высота наплыва, мм | 4,7 | 5,0 | 6,4»
превращается в предложение «Высота наплыва, мм — Эксперимент: 4,7; Расчет МКЭ: 5,0;
Отклонение, %: 6,4». Само по себе «4,7» ничего не значит, а такая строка находится
целиком.

**Чанкинг** идёт по структуре, а не по длине. Формула никогда не открывает кусок:
без вводной фразы по ней не понять, что за величины в ней стоят, поэтому граница
перед формулой не ставится, а если кусок всё же начинается с неё, к нему
приписывается предыдущий абзац. Заголовок раздела закрывает предыдущий кусок и
приписывается ко всем последующим как подсказка о контексте. Таблица идёт отдельным
куском, а если не помещается в бюджет — разбивается по строкам с повторением шапки.
Длина считается токенизатором той самой модели, которой куски пойдут на
векторизацию, иначе хвост молча обрезался бы на её стороне.

**Поиск гибридный.** Плотный вектор (`multilingual-e5-base`) понимает смысл запроса
и находит нужное, даже если слова не совпали, но плохо различает обозначения:
`Fe_2O_3` и `σ_т` для него почти одно и то же. Лексический поиск (BM25 с приведением
слов к основе для русского и английского) точен на символах и формулах, но
беспомощен к синонимам. Списки сводятся по рангу, поэтому кусок, поднявшийся в
любом из них, попадает в ответ. Отбор возможен по метаданным: только с формулами,
только с таблицами, только надёжный текст, по конкретным химическим элементам.

```bash
python -m pdfscan.rag.build search "восстановление оксида железа" --formula --element Fe
```

## Очистка корпуса

Разбор двухсот документов даёт около 192 тысяч блоков, и часть из них для поиска
бесполезна или вредна: шум распознавания с картинок и повёрнутых подписей,
колонтитул сборника на каждой странице, обрывки строк, разорванные разметкой
макета, и статьи, лежащие в корпусе дважды — отдельным файлом и внутри сборника.

Стадия устроена как последовательность файлов, а не один прогон: `ingest`
собирает все `blocks.jsonl` в Parquet, `clean` чистит, `audit` объясняет
результат. Порядок шагов внутри `clean` не произволен — мусор убирается первым,
чтобы не мешать считать повторяемость строк; колонтитулы вторыми, иначе они стоят
между абзацами разных страниц и не дают их сшить; склейка третьей, и только после
неё имеет смысл искать точные повторы.

Ничего не удаляется физически. У блока стоит `keep=false` и причина в
`drop_reason`, а текст остаётся рядом с исходным, поэтому порог меняется без
повторного разбора PDF, а по отчёту видно не только сколько выброшено, но и что
именно.

Словаря в детекторе шума нет намеренно: корпус двуязычный, металлургический и с
химией, поэтому любой внешний словарь отвергал бы половину законных слов —
«файнштейн», «фаялит», `ISASMELT`. Вместо принадлежности словарю считается
правдоподобие самой последовательности символов символьной моделью, обученной на
надёжном текстовом слое этого же корпуса. Признаки применяются с оглядкой на тип
блока: у формулы законно мало гласных и много знаков, и прозаические мерки к ней
не применяются вовсе.

```bash
python -m pdfscan.prepare.cli all                          # все стадии
python -m pdfscan.prepare.cli clean --garbage-threshold 0.5 # сдвинуть порог
python -m pdfscan.prepare.cli audit                        # только отчёт
```

Отчёт `reports/clean_audit.md` показывает выборки по полосам оценки шума:
по нему решается, куда двигать порог, — без примеров это выбор наугад.

## Повторное распознавание формул на сканах

На сканах формулы распознаются хуже всего: страницу читает модель, обученная на
прозе, и дробь превращается в две строки, а индексы — в обычные цифры. Но после
первого прохода есть рамка каждой формулы, а значит её можно вырезать и отдать
модели, которая занимается только формулами.

Этап живёт в отдельном окружении: paddle несовместим со стеком, на котором
работает разбор PDF.

```bash
brew install python@3.13        # PaddleX поддерживает Python до 3.13
/opt/homebrew/opt/python@3.13/bin/python3.13 -m venv .venv-formula
.venv-formula/bin/pip install -r requirements/formula-ocr.txt
.venv-formula/bin/pip install -e . --no-deps
```

Шаги разделены, потому что стоят по-разному: вырезка идёт минуты, распознавание —
часы, а при подборе порогов нужен только последний шаг.

```bash
venv/bin/python         -m pdfscan.formulas.ocr.cli crop
.venv-formula/bin/python -m pdfscan.formulas.ocr.cli recognize
venv/bin/python         -m pdfscan.formulas.ocr.cli apply --dry-run
venv/bin/python         -m pdfscan.formulas.ocr.cli apply
venv/bin/python         -m pdfscan.formulas.ocr.cli reclassify
venv/bin/python         -m pdfscan.formulas.ocr.cli revert   # вернуть как было
```

Отдельное окружение нужно только распознаванию: paddle тянет свою сборку и не
уживается с остальными зависимостями. Вырезка обходится `pypdfium2`, а отбор,
оценка и запись обратно — стандартной библиотекой, поэтому их удобнее запускать
из основного окружения; переклассификации оно уже необходимо, потому что там
загружается BERT.

Пересматриваются не все формулы, а три случая: текст пришёл от распознавания
страницы, в нём стоят битые `(cid:NN)`, или от формулы остался только её номер
вида `(3.2)` — то есть сама формула вставлена картинкой поверх текстового слоя.
Там, где текст собран из символьного слоя PDF, он точнее любой модели, и его не
трогают.

Замена происходит не всегда, и это главная часть этапа. Модель формул ошибается
иначе, чем распознавание страницы: она не рассыпает текст, а уверенно выдаёт
гладкую, но чужую разметку. Поэтому кандидат проверяется на парность скобок и на
срыв в повтор одного куска, сравнивается с исходным по числу признаков
математической структуры, а спорные случаи получают решение `unsure` и по
умолчанию не применяются — плохая, но заметная формула лучше подменённой.

Последний шаг, `reclassify`, пересчитывает подтип у тех блоков, которым замена
сменила текст. Без него метка остаётся от прежней, нечитаемой записи, а по ней
при индексации решается, искать ли в блоке символы элементов: формула, от
которой в разборе остался огрызок `Cu?*(aq)`, получила тип `Formula` без
подтипа и после замены так и осталась бы невидимой для запроса «медь». Порядок
решения тот же, что при разборе, — сначала грамматика химического уравнения,
потом модель, — иначе одинаковые уравнения получили бы разные подтипы в
зависимости от того, коснулось их распознавание или нет.

Результат пишется в те же `blocks.jsonl`, иначе следующие этапы пришлось бы учить
выбирать между двумя источниками правды. Правка обратима и прослеживаема: рядом
появляется `blocks.jsonl.orig`, прежний текст остаётся в блоке в поле
`text_original`, решение с обоснованием — в `formula_ocr`, а сводка по документу —
в `formula_ocr.jsonl` рядом с ним. Файл пишется во временный и переставляется
одним вызовом, поэтому обрыв на середине не оставляет корпус в смешанном виде.

## Запуск в Google Colab

`notebooks/colab_pipeline.ipynb` разбирает документы и собирает индекс на машине Colab.
Видеокарта ускоряет модель разметки макета и векторизацию, но само распознавание
(tesseract) считается на процессоре и от неё не зависит — на сканах выигрыш будет
скромнее, чем на документах с текстовым слоем. Разбор идёт по одному документу и
сразу складывает результат на Google Диск, поэтому обрыв сеанса не сжигает работу:
при повторном запуске уже готовые файлы пропускаются.

## Что стоит улучшить

Дальше — по убыванию пользы.

**Строки вне рамок макета теряются.** От трёх до шести строк на документ не попадают
ни в один блок `unstructured` и пропадают из выгрузки совсем. В англоязычном образце
так потерялась дробь вместе с двумя абзацами. Для RAG потеря содержимого хуже
ошибки в классе, поэтому это первое в очереди. Лечится добавлением осиротевших строк
как отдельных блоков по геометрии.

**Символы без таблицы юникода.** В `test2.pdf` держатся 57 символов вида `(cid:31)`:
шрифт `SymbolMT` вставлен без таблицы соответствия, и формулы выглядят как
`(cid:31)Mn_{i}R_{i}`. Читается из встроенной в шрифт таблицы имён глифов. Для
формул это отчасти закрыто повторным распознаванием по рамке, но `(cid:NN)` в
обычном тексте остаётся.

**Порог отбора шума не выверен.** При текущем значении 0.6 отбрасывается 264 блока,
а в полосе 0.4–0.5 в отчёте видны подписи к рисункам, распознанные вверх ногами, —
то есть заведомый мусор, который проходит. Порог явно стоит опускать, но решать это
надо по выборкам из отчёта, а не наугад.

**Надёжность распознанных формул.** Блок, пересмотренный моделью формул, остаётся
с `reliable=false`, потому что это поле означает «собрано из текстового слоя», и
менять его смысл задним числом нельзя. Но при поиске с ключом `--reliable` такие
формулы отсеиваются вместе с настоящим мусором. Нужен отдельный уровень доверия
между текстовым слоем и распознаванием страницы.

**Таблицы.** Во всём корпусе ровно одна таблица, проверять качество не на чем.
Разбор и раскладка по строкам написаны и на ней работают, но структура таблицы
(`text_as_html`) не пересобирается из текстового слоя, то есть внутри неё до сих пор
текст от распознавания со всеми искажениями.

**Качество поиска не измерено.** Индекс собирается и отвечает осмысленно на
проверочных запросах, но набора «запрос — правильный ответ» нет, поэтому сказать,
насколько он хорош, нечем. Нужен небольшой размеченный список вопросов по корпусу.

**Оценка классификатора.** Тридцать один настоящий пример против примерно тысячи
синтетических, причём собранные примеры вошли в обучение, поэтому проверка на тех же
документах не независима. Честную оценку даст отложенный документ, который модель не
видела.
